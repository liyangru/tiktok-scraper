# 多端适配与瘦身评估

> 结论先行：**macOS 可以直接搬，鸿蒙不能直接搬，体积能砍一半以上但代价是改架构。**
> 本文所有体积数字都是 2026-10-11 在本机实测出来的，不是估的。

---

## 一、基线：现在到底背了什么

### 安装包

| 项 | 大小 |
| --- | --- |
| `TikTokScraper-1.0.1.exe`（portable，压缩后） | **299.0 MB** |
| └ `TikTokScraper.exe`（Electron 运行时） | 234.9 MB |
| └ `resources/browser-payload.tar.gz`（抓取用 Chromium） | 199.3 MB |
| └ `resources/app.asar`（应用代码 + 生产依赖） | 127.3 MB |
| └ `locales/*.pak`（48 种语言包） | 约 40 MB |
| └ 其余 pak / dll（d3d、swiftshader、icu…） | 约 50 MB |

**关键结构问题：这个应用同时跑两个完整的 Chromium。**
一个是 Electron 给自己 UI 带的（234.9MB），一个是给 patchright 抓取带的（199.3MB）。
磁盘和内存的大头都是它俩。

### 本机占用（不影响安装包，但占用户磁盘）

| 项 | 大小 | 说明 |
| --- | --- | --- |
| `dist/` | **1659.0 MB** | pkg 单文件构建的产物，**已被 Electron 路线取代，纯垃圾** |
| `data/` | 437.4 MB | 运行时数据 |
| └ `data/profiles` | 304.8 MB | 抓取用 Chromium 的用户档案，缓存会一直涨 |
| └ `data/profiles-seller` | 37.8 MB | 卖家中心账号档案 |
| └ `data/_test_*`（3 个） | 60.1 MB | 测试残留 |
| └ `data/jobs` | 15.2 MB | 抓取任务 |
| `node_modules/` | 545.5 MB | 开发态，不进安装包 |

### node_modules 里能点名的大头

`electron` 371.3MB（devDependency，不进包）、`electron-winstaller` 30.7MB、
`exceljs` 20.8MB、`playwright-core` 13.0MB、`patchright-core` 12.9MB、
`@esbuild/win32-x64` 11.2MB、`patchright` 4.9MB、`playwright` 4.8MB。

> `playwright` 这个包**运行时根本没被 require 过**（只有 `patchright` 和兜底的 `playwright-core`），
> 它唯一的用途是 `scripts/build-mac.sh` 里 `npx playwright install chromium` 下载浏览器载荷。
> 挪到 devDependencies 白赚 4.8MB。

## 二、内置播放器和其它依赖能不能搬

| 依赖 | macOS | 鸿蒙（手机/平板） | 鸿蒙 PC |
| --- | --- | --- | --- |
| **内置播放器**（HTML5 `<video>`） | ✅ 原样可用 | ✅ **ArkWeb 是 Chromium 内核，完整支持 HTML5 video** | ✅ |
| Node + Express 本地服务 | ✅ 原样 | ❌ 没有 Node，只能换成云托管 | ⚠️ Electron 移植版里有 |
| patchright / playwright 驱动 | ✅ 原样 | ❌ **完全跑不了** | ⚠️ 要真机验证 |
| 抓取用的独立 Chromium 二进制 | ✅ 换 arch 版 | ❌ 跑不了 | ⚠️ 要真机验证 |
| exceljs（报表导出） | ✅ | ⚠️ 云端跑，导出的文件回传 | ✅ |
| 本机文件/文件夹选择 | ✅ `dialog.showOpenDialog` | ⚠️ 要换成 ArkUI 的文件选择器 | ⚠️ |
| tar / 模块下载安装 | ✅ | ⚠️ 要换实现方式 | ⚠️ |

**播放器是最不用担心的那个** —— 它就是 `index.html` 里一行
`<video id="playerVideo" controls playsinline>`，纯 HTML5，任何 Chromium 内核的壳都能放。
真正搬不动的只有一个东西：**patchright + 它驱动的 Chromium**。

## 三、macOS：能搬，而且比你想的近

### 已经准备好的

- `scripts/build-mac.sh` 完整脚本已在（依赖安装 → 图标 → 分架构下载浏览器 → electron-builder → ad-hoc 签名）
- `scripts/make-icon.js`、`scripts/verify-mac-payload.py` 都在
- `package.json` 里 `build.mac` 配置已写好（zip，arm64/x64，`identity: null`）
- **`browser-payload-mac-arm64.tar.gz` 173.3MB 和 `browser-payload-mac-x64.tar.gz` 181.5MB 都已经下好了**
- `lib/browsers.js` 里 macOS 的解压路径（`chrome-mac-arm64/Chromium.app/Contents/MacOS/Chromium`）已经写了
- `lib/scraper.js:38 resolveChromePath()` 里 macOS 的 Chrome/Chromium/Edge 路径已经列了

### 还缺什么

1. **必须在 macOS 上构建**。electron-builder 明确禁止跨平台出 mac 包；
   Apple Silicon 的签名也只能用 macOS 的 `codesign`。脚本里已经防了这个（`uname -s` 检查）。
2. **签名二选一**（这是唯一的决策点）：
   - ad-hoc 签名（免费，脚本已做 `codesign --force --deep --sign -`）：
     能跑，但用户第一次打开会被 Gatekeeper 拦，要「右键 → 打开」或
     `xattr -dr com.apple.quarantine /Applications/TikTokScraper.app`。
   - Developer ID + 公证（**99 美元/年**）：双击直接开，无警告。要上架/发给客户只能走这条。
3. **浏览器版本不能乱换**。`build-mac.sh` 里已经写明：能过 TikTok 反爬的是
   **playwright 1.64 对应的 chromium-1248（Chrome for Testing 156.0.8078.4）**，
   patchright 1.63 自带的 chromium-1243 / Chrome 153 版本对不上。
   这条是实测结论，别图省事改成 patchright 自己下载。
4. arm64 和 x64 的浏览器载荷**不能交叉生成** —— 要出两个包就得两台机器（或用 M 系列 + Rosetta）。

### 结论

**出 mac 包的工作量 ≈ 找一台 Mac 跑一遍 `bash scripts/build-mac.sh`。** 代码层面基本不用改。

## 四、鸿蒙：不能直接搬，必须拆

### 分两种情况，差别巨大

**A. 鸿蒙手机 / 平板（HarmonyOS NEXT）**

- 没有 Electron，**没有 Node.js**，纯鸿蒙内核，**不兼容 Linux ABI** —— 整套 Electron 外壳直接判死。
- 只能用 **ArkTS + ArkUI** 原生重写。
- 好消息：`ArkWeb`（Web 组件）是**基于 Chromium 内核**的，
  HarmonyOS 6.0 = M132、7.0 = M144，HTML5 的 `<video>`、`<audio>` 完整支持。
  → **把整个前端塞进一个 Web 组件是可行的，播放器不用重写。**
- 坏消息：`patchright` 和它驱动的 Chromium **在这上面没有任何可能跑起来**。
  → 抓取必须搬到云端，端上只剩 UI。

**B. 鸿蒙 PC**

- 有 Electron 的鸿蒙移植（预编译包 v34，要求 HarmonyOS NEXT API 20+），
  靠 Linux 兼容层跑 Node —— **理论上 Node + Electron 能跑**。
- 但**抓取用的那个独立 Chromium 二进制能不能在鸿蒙 PC 上跑，没人验证过**。
  就算 Electron 起来了，抓取这一半仍然是未知数。

### 拆法（用腾讯云开发）

```
鸿蒙端（ArkUI 壳 + ArkWeb 或直接 ArkUI）
   ↓ HTTP（HTTP 访问服务 / 云托管域名）
云托管 CloudBase Run（容器）
   ├─ Express 服务（现有 server.js 几乎不用改）
   ├─ patchright + Chromium（现有载荷直接做成镜像）
   └─ 账号档案 → 云存储（必须外置，云托管是无状态的）
云存储 + 云数据库（视频、报表、账号档案）
```

云托管（CloudBase Run）确认支持：任意语言/框架容器、**不用本地 Docker**（可上传代码包或授权 Git
仓库由云端构建）、支持锁死 min=max=1 实例跑长任务。

### 三个必须提前知道的坑

1. **出口 IP 变了。** 现在抓取走的是你本机 IP，上云后变成腾讯云机房 IP。
   TikTok 风控与 IP 强相关，很可能要重新调代理/反爬策略。**这是最大的未知数。**
2. **违背「数据不上云」这条现有产品原则。** 账号凭据与登录态要存到云端，
   这是产品定位的变化，不是纯技术问题 —— 需要你拍板。
3. **云托管是无状态的。** `data/profiles` 这种浏览器登录档案每次都得从云存储拉下来、
   用完传回去，这块要新写代码。

## 五、瘦身：能砍多少，代价是什么

按「收益 / 风险」排序：

| # | 动作 | 省下 | 风险 |
| --- | --- | --- | --- |
| 1 | 删掉 `dist/`（pkg 产物，已废弃） | **本机 1.66 GB**（不影响安装包） | 无 |
| 2 | `playwright` 挪到 devDependencies | 安装包 ~5 MB | 无 |
| 3 | `afterPack` 钩子里删掉用不到的 `locales/*.pak`（只留 zh-CN / en-US / th） | 未压缩 ~38 MB | 低 |
| 4 | 定期清理 `data/profiles` 缓存 + 清掉 `_test_*` | 运行时 360 MB+ | 低 |
| 5 | Chromium 载荷**不进安装包**，首次运行时才下载 | 安装包 **299 → 约 100 MB** | 中：首次要联网下 200MB，内网环境直接卡死 |
| 6 | 优先用系统 Chrome/Edge，载荷只当兜底 | 同上（且不动安装包） | 中：**换浏览器 = 换指纹，TikTok 是否放行必须实测** |
| 7 | 抓取上云托管 | 客户端 −199MB 载荷 −31MB 驱动 | 高：改出口 IP + 数据上云 |
| 8 | Electron 换成 Tauri（用系统 WebView，不带 Chromium） | 安装包 **→ 20~40 MB** | 高：后端要 Rust，或用 sidecar 挂 Node（那还是带 Node） |

### 关于第 6 条，现成的便宜

`lib/scraper.js:38 resolveChromePath()` **已经支持用系统浏览器了** ——
它按 `CHROME_PATH` 环境变量 → Windows 的 Chrome/Edge → macOS 的 Chrome/Chromium/Edge
→ Linux 的 chromium 顺序找，全都找不到才回退到自带载荷。
所以「不装 199MB 载荷」这条路**代码已经通了**，缺的只是一次真机验证：
**用系统 Edge 时 patchright 的反检测补丁还灵不灵、TikTok 放不放行。**
这是性价比最高的一次实验 —— 一行环境变量就能测。

### 内存（RAM）

现在同时驻留**两个完整 Chromium**（Electron UI + 抓取浏览器），这是内存的大头。
抓取上云后，客户端只剩一个。

## 六、内核有没有更小更好用的

| 方案 | 能省 | 结论 |
| --- | --- | --- |
| **Tauri**（Rust + 系统 WebView2/WKWebView） | Electron 的 235MB | 客户端能到 30MB 级。但要动后端：重写成 Rust，或用 sidecar 挂 Node（那 Node 还是得带上）。**适合和「抓取上云」一起做**，单做收益有限 |
| **chrome-headless-shell / @sparticuz/chromium** | 载荷的一半 | ❌ **不推荐**。它们没有 patchright 的协议层反检测补丁，headless-shell 的指纹更明显，基本可以判定会被 TikTok 拦。别为省 100MB 牺牲抓取成功率 |
| **直接驱动 Electron 自带的 Chromium**（connectOverCDP） | 199MB 载荷 + 一份常驻内存 | ⚠️ 理论最优、风险最高。patchright 的补丁是 launch 时注入的，走 CDP 连上去不一定生效；且 Electron 的 Chromium 带 Node 集成、指纹异常。**只值得做一次探针实验** |
| 保持 patchright | — | ✅ 抓取成功率优先的话，这个不能动 |

---

## 七、建议的执行顺序

1. **先出 mac**（成本最低、脚本就绪、载荷已备好）—— 找台 Mac 跑一遍 `build-mac.sh`。
2. **同时做一次「系统 Edge 抓取」探针**：`CHROME_PATH` 指向 Edge，跑一次真实搜索，
   看 TikTok 放不放行。通过了就白捡 199MB。
3. **做一个只跑抓取的云托管探针**（不改客户端）：验证云端 Chromium 能不能过 TikTok、
   云端出口 IP 会不会被风控。这是鸿蒙路线和大幅瘦身路线的**共同前置条件**。
4. **探针通过后再决定**：要不要把抓取搬上云、客户端要不要换 Tauri。
5. **鸿蒙排在最后**，等第 3 步的探针结果；而且要你先明确目标是**鸿蒙 PC** 还是**鸿蒙手机/平板**
   —— 一个是「等 Electron 移植成熟」，一个是「ArkUI 重写前端」，工作量差一个数量级。

### 需要你拍板的三件事

1. 抓取要不要上云？（决定客户端能不能瘦到 100MB 以下；代价是换出口 IP + 数据上云）
2. mac 走免费 ad-hoc 签名（用户要右键打开）还是交 99 美元/年做公证（双击直接开）？
3. 鸿蒙的目标是手机/平板还是 PC？
